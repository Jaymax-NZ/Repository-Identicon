# The identity section: the change set

**Executed 2026-08-31**, in three commits on `diagram-walk`. Every item in the
change set below is done. The rules are kept here because they are the record
of what was decided and why, and `SPEC.md` states only the outcome.

Two things settled during execution rather than before it, both recorded here
because neither was an explicit instruction:

- **The seed is not lowercased.** The argument for folding was that forges
  treat owner and repository names case-insensitively, so two people could
  derive different seeds for one project. Rule 3 removes it: derivation runs
  once and the result is committed, so there is no second derivation to
  disagree. Against folding: it destroys a name the reader recognises, and it
  makes every port implement Unicode case mapping to stay conformant.
  `vectors.json` pins two spellings of one name so a port that folds fails on
  that pair.
- **A `colourMap` this build does not implement raises `UnknownColourMap`.**
  One equality check. It can only be reached by a hand edit, and drawing with
  the only map there is would produce a mark `settings.json` does not
  describe.

## What was decided, 2026-08-31

1. **The seed is the normalised string derived from the repository, and
   nothing else.** Either `owner/repo` from the git remote, or a local
   filesystem path where there is no remote to read. The host is dropped.
2. **The seed lives in `.identicon/settings.json` and nowhere else.** That
   file is the only input to a repository's identity.
3. **The seed is written only when it is not set.**
4. **`--reseed` moves the current seed into a `identiconSeedHistory` array and blanks
   the current seed.** It does nothing else. Rule 3 then derives a new seed
   and writes it, so reseeding is one rule applied to an emptied field rather
   than a second way of setting one.
5. **Existing repositories are ignored.** Nothing migrates. Everything is
   experimental at this stage.
6. **`settings.json` is an input, not an artifact.** It is not in
   `artifact_names`, is not compared byte-for-byte against generated bytes,
   and gets no `.prior` copy.
7. **`apply --check` on an unseeded repository reports the seed it would
   write**, and writes nothing.
8. **There is no key.** The concept goes completely. The digest is taken of
   the seed, by itself.
9. **The colour map is a setting in `settings.json` and never enters the
   digest.** A better colour map must change colours and never shapes: adding
   a colour to the palette is not a reason for an identicon's pattern to move.
10. **There is one colour map.** Shipping a second one is a significant update
    and may never happen. Until it does, nothing has to select between maps.
11. **A repository's `colourMap` is written at seeding and locked in.** No
    command changes it. Changing one is a hand edit of `settings.json`. The
    functionality to move a repository between maps is needed when a second
    production map ships, and not before.
12. **`identiconSeedHistory` is most recent first.**
13. **`MAPPING_VERSION` is renamed `COLOUR_MAP_LATEST`.** It names the newest
    shipped colour map, which is what a repository is seeded with. The JSON
    key is `colourMap`.
14. **`COLOUR_MAP_LATEST` is the integer `0`.** The old `"0.3"` was a string
    because the value went into the hashed key, where `"0.3"` and `"03"` are
    different keys. Rule 9 takes it out of the hash. What is left is an
    equality check and a numbered sequence of maps, so the natural type is an
    integer. The second map is `1`.
15. **Colour maps ship as files carrying the digit in the filename, and a
    build learns which maps it has by seeing which files are present.** With
    one map this is a comment and not code. Nothing discovers anything until
    a second map ships.
16. **One normalisation function applies to whatever is in the seed field**,
    whether this tool derived it or a person typed it. Hand-editing a seed is
    a supported thing to do.
17. **Names are self-documenting, in the file and in the code.** The seed
    field is `identiconSeed`, not `seed`, so a person reading `settings.json`
    knows what the string is for without opening the specification. The history
    list is `identiconSeedHistory`.
18. **A stored seed survives a clone, whatever it was derived from.**
    `settings.json` is committed, so a path-derived seed travels exactly as a
    remote-derived one does. Derivation runs once in a repository's life.
    Choosing the remote first is a statement about which derivation is stable
    across machines at seeding time, and says nothing about what survives
    afterwards. Reseeding is on request and never automatic.

## The file

```json
{
  "identiconSeed": "owner/repo",
  "identiconSeedHistory": [],
  "colourMap": 0
}
```

`identiconSeed` is written when it is not set, and never rewritten.
`identiconSeedHistory` holds the seeds this repository has had, most recent
first; `--reseed` pushes the current seed onto its front and blanks
`identiconSeed`. `colourMap` is written at seeding and never rewritten.

**This file is committed, with the rest of `.identicon/`.** That is what makes
a stored seed survive a clone, and it is why derivation runs once in a
repository's life rather than on every run.

A `colourMap` this build does not implement is refused rather than drawn with
the only map there is, because drawing it silently would produce a mark the
file does not describe. That is one equality check and one error, and it is
the whole of what rule 10 leaves to do.

## Facts checked against the source

- There is exactly one hash. `_digest` is MD5 over the input string, and it is
  the only hash in `repository-identicon.py`, `text-identicon.py` or the tests.
- `identicon_grid` reads the first 15 hex characters of that digest, one per
  cell of the left three columns. `identicon_hue` reads the last 7 as 28 bits
  over `0xfffffff`. Both read the same digest.
- MD5 stays. The reference implementation this conforms to consumes MD5 hex,
  so changing the hash ends conformance. Its collision weakness matters where
  forging a match gains something, which is not the case here.

## Consequences accepted

- Dropping the host makes `github.com/a/b` and `gitlab.com/a/b` one seed, so
  one mark. A repository that needs to differ writes its own seed into
  `settings.json` before the first `apply`.
- Every mark changes. `vectors.json`, `tests/fixtures/` and the four fixture
  directories are regenerated on this branch.
- Taking the version out of the digest makes a grid vector independent of the
  colour map. `vectors.json` splits into seed, md5 and grid, which no colour
  map affects, and foreground, which one does.
- The `identity` branch was opened on the condition that the key changes
  exactly once. There is no key. Both branch descriptions have been rewritten.
- `overridden_remote` is removed. It was kept as candidate 14 on 2026-08-30 to
  report a rename arriving under a pinned seed. Under rule 3 every seed is
  stored on the first run, so that state is `seed_drift` and not a second
  thing.

## The normalisation, under rule 16

Three functions today do two jobs between them, and the boundary is in the
wrong place: `normalise_seed` expands and absolutises a path *and* strips it,
while `normalise_remote_url` parses a URL *and* lowercases it. A hand-edited
seed passes through neither.

Split so that derivation is separate from normalisation:

| function | job |
|---|---|
| `remote_seed(url)` | a git URL to `owner/repo`. Parsing only |
| `path_seed(path)` | a directory to an absolute path. Expansion only |
| `normalise_seed(value)` | the one normaliser: strip whitespace, lowercase, strip trailing separators |

`normalise_seed` runs on every seed, from all three origins: derived from a
remote, derived from a path, and read from `settings.json`.

**One consequence.** The single normaliser lowercases, because `Owner/Repo`
and `owner/repo` must be one identicon and that was deliberate. Lowercasing
then also reaches path seeds, so `/src/Foo` and `/src/foo` derive one seed on
a case-sensitive filesystem. Reaching that needs two sibling directories
differing only in case, both unseeded, on one machine, and rule 16 makes the
repair a hand edit. Normalisation runs once, at seeding, so the collision
cannot appear later.

## The format: JSON

`repository-identicon.py` is standard library only, and this tool writes the
settings file as well as reading it. `json` reads and writes. `tomllib` reads
only, and no standard library module writes TOML. YAML is not in the standard
library at all. A port in another language has to read this file, which argues
the same way.

The cost is that JSON has no comments, so a person hand-editing a seed under
rule 16 cannot write down why they did.
